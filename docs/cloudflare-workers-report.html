0まず結論

従来の「ReactをCaddyで配信し、GoプロセスがWebSocketとメモリ上のキャンバスを管理する」 構成を、Cloudflare上の3要素へ置き換えました。

配信 Reactの生成物をWorkers Static Assetsから配信
リアルタイム処理 Workerが/wsをDurable Objectへ転送
状態管理 Durable Objectが接続とセルを一元管理・永続化
現在の状態： Python版をデプロイ済み Wranglerのデプロイ履歴で、python_workersを有効にした最新版が 100%のトラフィックを受けていることを確認済みです。

サーバーOS、Goプロセス、Caddy、コンテナを常時運用する代わりに、 Cloudflareが実行環境・配信・状態を管理します。一方で、通常のWorkerは永続的なメモリを 持てないため、共有キャンバスのような状態にはDurable Objectが必要です。

1Cloudflareの技術をどう捉えるか

W

Workers

HTTPリクエストを受けてコードを実行するサーバーレス環境です。Node.jsサーバーを 1台起動し続けるのではなく、Cloudflareのネットワーク上でfetch()が呼ばれます。

DO

Durable Objects

「名前を持つ1つの処理主体」と専用ストレージを組み合わせた仕組みです。 複数利用者を同じObjectへ集め、順序のある更新やWebSocketを調整できます。

A

Static Assets

Viteが生成したHTML・JavaScript・画像などをWorkerと一緒に配信する機能です。 この構成ではCloudflare Pagesを別に作る必要がありません。

Wr

Wrangler

Cloudflare Workers用のCLIです。Python Workerではpywranglerが Pythonの準備とbundleを担当し、内部でWranglerと連携します。

重要な考え方： 通常のWorkerは高速で分散実行されますが、そのぶん「この前のリクエストと同じメモリへ届く」 とは考えません。共有状態が必要な部分だけを、名前で特定できるDurable Objectへ集めます。

2このアプリの全体構成

図1：ブラウザから見た配信経路と、Cloudflare内部での責務分担

なぜ1つのDurable Objectなのか

現在の仕様は「全利用者が同じ1枚を編集する」ため、全接続を固定名globalの Objectへ送っています。同じ名前からは同じObject IDが得られるため、更新の集約点になります。 Go版で1つだったHubを、Cloudflare上の1つのActorへ移したイメージです。

将来のスケール上の注意： 1つのObjectは整合性を保ちやすい反面、負荷の集中点でもあります。利用者やメッセージ数が 増える段階では、roomIdごとにDurable Objectを分ける設計が基本になります。

3実際の通信はどう流れるか

質問への短い答え： 「ページを取得した後、Reactが/wsへ接続する」は合っています。 ただし、最初のページ取得では通常worker/src/entry.pyのWorkerコードは実行されません。 Static AssetsがHTMLやJavaScriptを直接返します。/wsへの接続時にトップレベルWorkerの fetch()が一度呼ばれ、接続をDurable Objectへ渡します。接続成立後の drawはDurable ObjectのwebSocketMessage()が直接処理します。

どの処理が、いつ呼ばれるか

段階リクエスト／イベント主に動く場所呼ばれるコード
1. ページ取得 GET /、JS、CSS、画像 Workers Static Assets 通常はsrc/entry.pyを通らず、Assetが直接返る
2. 接続開始 GET /ws + WebSocket Upgrade トップレベルWorker Defaultクラス側のfetch()
3. 接続の受理 WorkerからDOへ転送したUpgrade CanvasDurableObject DOクラス側のfetch()
4. 描画 接続済みWebSocket上のdraw CanvasDurableObject webSocketMessage()
5. 異常 WebSocketエラー CanvasDurableObject webSocketError()
6. 切断 WebSocket Close CanvasDurableObject webSocketClose()

src/entry.pyという1ファイルに「入口となるWorker」と「状態を持つDurable Object」の 両方が書かれているため紛らわしく見えます。しかし、ファイル全体が接続中ずっと上から順に 動き続けるわけではありません。Cloudflare runtimeが、到着したイベントに対応するhandlerだけを 呼び出します。

Hibernationとは

WebSocketは接続が長時間続きますが、ずっとメッセージが流れるとは限りません。 Hibernation APIを使うと、アイドル時にDurable Objectの実行コンテキストがメモリから 退避しても、接続はCloudflare側で維持されます。次のメッセージでObjectが再開します。

退避時にはインメモリ状態が消えるため、キャンバス本体は必ずDO Storageへ保存します。 接続一覧は自前の配列ではなく、再開後もランタイムからgetWebSockets()で取得します。

5Python実装に何を書いたか

src/entry.py

Workerのルーティング、DOクラス、WebSocket接続、保存、broadcastを実装。

src/protocol.py

メッセージ型、128×128の制約、JSON検証、ストレージキーを定義。

tests/test_protocol.py

正常なdraw、不正JSON、範囲外座標、空色、キー順序をテスト。

pyproject.toml

Python 3.12、workers-py、runtime SDK、Ruffを定義。

Python Workersはベータ： PythonはCPython/PyodideをWebAssemblyとしてWorkers runtime内で動かします。 JavaScript製のWorkers APIはFFIを通して呼び出せますが、仕様更新の影響を受ける可能性があるため、 本番運用ではCloudflareのリリースノートと既知の制約を確認します。

Bindingは「Cloudflareが渡してくれる接続口」

stub = self.env.CANVAS.getByName("global")
return await stub.fetch(request)

return await self.env.ASSETS.fetch(request)

ASSETSやCANVASを自分でnewすることはありません。 wrangler.jsoncの定義に基づいてCloudflare runtimeがenvへ渡します。 D1、KV、R2、Secretなどを将来追加する場合も、基本的に同じbindingの考え方です。

Durable Objectを使うために必要な記述の全体像

Durable Objectはクラスを書くだけでは利用できません。設定とコードの対応が必要です。 このプロジェクトでは次の8段階を記述しています。

段階記述場所記述内容役割
1wrangler.jsoncdurable_objects.bindingsbinding名と実装クラス名を結び付ける
2wrangler.jsoncnew_sqlite_classesSQLiteベースのDOクラスをCloudflareへ登録する
3wrangler.jsoncpython_workersPython runtimeを有効にする
4src/entry.pyclass ... (DurableObject)Cloudflareが起動するDOクラスを実装・公開する
5Workerのfetch()getByName()対象Objectのstubを取得する
6DOのfetch()WebSocketPairとacceptWebSocket()WebSocket Upgradeを受理する
7DOのevent handlerwebSocketMessage()接続後のメッセージを処理する
8DOのevent handlerctx.storageとgetWebSockets()状態の永続化と全接続への配信を行う

1. bindingとmigrationを宣言する

"durable_objects": {
  "bindings": [{
    "name": "CANVAS",
    "class_name": "CanvasDurableObject"
  }]
},
"migrations": [{
  "tag": "v1",
  "new_sqlite_classes": ["CanvasDurableObject"]
}]
  • name: "CANVAS"はWorkerコードから使うbinding名です。
  • class_nameはPythonモジュール直下のクラス名と完全に一致させます。
  • new_sqlite_classesは、新規クラスにSQLite-backed storageを割り当てます。
  • tag: "v1"はDOクラス構成の履歴です。将来の変更はv2として追記します。

2. Python Workers runtimeを有効にする

"main": "src/entry.py",
"compatibility_flags": ["python_workers"]

mainはPythonモジュールを指定し、互換フラグでPython runtimeを有効にします。 Pythonの標準入口はWorkerEntrypointを継承したDefaultクラスです。

3. Cloudflareが起動できるPythonクラスを書く

from workers import DurableObject

class CanvasDurableObject(DurableObject):
    async def fetch(self, request):
        # WebSocket Upgradeを受理する
        ...

クラスをモジュール直下へ定義すると、Wranglerのclass_nameからruntimeが見つけます。 DurableObjectを継承すると、self.ctxから専用ストレージや Hibernation WebSocket APIを利用できます。

4. 固定名から同じObjectを選び、stubへ転送する

stub = self.env.CANVAS.getByName("global")
return await stub.fetch(request)

getByName("global")は、同じ名前から常に同じIDを決め、そのObjectへ操作を送る stubを取得します。 stub.fetch(request)でWebSocket Upgradeを転送します。Objectは必要になった時点で Cloudflareが遅延起動します。

5. DO側でWebSocket接続を受理する

client, server = WebSocketPair.new().object_values()

self.ctx.acceptWebSocket(server)

return Response(None, status=101, web_socket=client)
  • WebSocketPairは、クライアント側とサーバー側の2端点を作ります。
  • clientはHTTP 101レスポンスに載せてブラウザへ返します。
  • serverはDurable Objectが保持します。
  • ctx.acceptWebSocket(server)を使うことでHibernation対応になります。
似た名前のfetch()に注意： トップレベルWorkerのfetch()は公開URLの入口、DOクラスのfetch()は stubから転送されたリクエストの入口です。同じ名前でも、別のオブジェクトに属する別handlerです。

6. 接続後は専用handlerでメッセージを受ける

async def webSocketMessage(self, _socket, message):
    # validate → persist → broadcast
    ...

一度101で接続が成立した後は、各メッセージについてトップレベルWorkerのfetch()を 再実行しません。Cloudflare runtimeが、接続を受理したDOのwebSocketMessage()へ イベントを直接配送します。DOがHibernation中なら、このイベントで再起動してからhandlerを呼びます。

7. 重要な状態をDO専用ストレージへ保存する

await self.ctx.storage.put(
    "cell:009:007",
    {"x": 7, "y": 9, "color": "#123456", "updatedAt": 1710000000000},
)

新しいSQLiteベースのDurable Object上で、key-value形式のStorage APIを利用しています。 これはCloudflare KVという別製品ではなく、そのObject専用の強整合ストレージです。

接続時にはawait self.ctx.storage.list({"prefix": "cell:"})で全セルを読み、 snapshotを作ります。描画時は配信より先にput()を完了させるため、 他のクライアントが受け取った描画が再接続後に消える状態を避けています。 SDKがJavaScriptのMapをPythonのdictへ変換するので、 TypeScript版と同じ保存データをそのまま利用できます。

8. ランタイム管理の接続一覧へbroadcastする

for socket in self.ctx.getWebSockets():
    socket.send(payload)

接続一覧をクラスプロパティやグローバル変数へ保存しません。Hibernationや再起動でメモリは 消えるため、接続はランタイム管理のgetWebSockets()から毎回取得します。 キャンバス状態はStorage、現在の接続はWebSocket runtime、という責務分担です。

このDOに__init__がない理由

現在はSQL table作成などの初期化処理も、復元が必要なインメモリキャッシュもないため、 明示的な__init__は不要です。将来SQL schemaを作る場合は__init__で ctx.blockConcurrencyWhile()を使って初期化できますが、通常のメッセージ処理全体を そこで囲むと同時処理性能を落とすため、初期化だけに限定します。

6ローカル開発から公開まで

worker/package.jsonに、複数ディレクトリをまたぐ処理を npm scriptとしてまとめました。コマンドを覚えるより、目的に応じてscriptを選べば済みます。 Pythonの依存関係はpyproject.tomlとuv.lock、Workers runtime向けの 解決結果はpylock.tomlで固定します。

Node.jsは22 LTSを使用： 現在のpywrangler 1.16.2が利用するPyodideは、Node.js 26で削除された Wasmオプションをまだ使用します。このリポジトリは.node-versionと package.jsonでNode 22系を指定しています。
目的コマンド内部で行うこと
ローカル起動npm run devVite build → pywrangler dev
総合チェックnpm run checkRuff、Pythonテスト、フロントlint/build、deploy dry-run
構成確認用ビルドnpm run buildVite build → pywrangler deploy --dry-run
Cloudflareへ公開npm run deployVite build → pywrangler deploy

初回に実際に行ったこと

  1. uv syncでPython依存を導入し、uv.lockを生成。
  2. Ruff、Pythonプロトコルテスト、フロントのlintとbuildを実行。
  3. dry-runでWorker bundle、Assets、DO binding、migrationを検証。
  4. pywrangler devでローカルWorkerとローカルDO Storageを起動。
  5. 複数WebSocketへのbroadcastと、再接続後のsnapshot復元を確認。
  6. Python版をCloudflareへデプロイ。
  7. デプロイ履歴からpython_workers版が100%配信中であることを確認。
デプロイ時に自動で行われること： Workerコードのbundle、静的アセットのアップロード、binding設定、DOクラスmigration、 新バージョンへの切り替えです。別途D1やKVを手作業で作る工程はありません。

7日常運用で使うもの

ローカルで試す

cd worker
npm run dev

通常はhttp://localhost:8787で起動します。ローカルの状態は.wrangler/配下です。

変更前に確認する

cd worker
npm run check

Python lint・テスト・フロント・Wrangler設定をまとめて検証します。

本番ログを見る

cd worker
npx wrangler tail

Workerで発生したリクエストログや例外をリアルタイムに確認します。

バージョンを確認する

cd worker
npx wrangler deployments list

どのバージョンが何%のトラフィックを受けているか確認します。

設定変更の基本ルール

  • wrangler.jsoncをCloudflare構成の正本としてGit管理する。
  • bindingを追加・変更したらPythonのself.env.<名前>と一致させる。
  • Python Workersはベータなので、workers-pyとruntime SDKの更新時にスモークテストする。
  • DOクラス構成を変えるときは既存tagを編集せず、新しいmigration tagを追加する。
  • APIキーなどの秘密情報は設定ファイルへ書かず、wrangler secret putを使う。
  • compatibility_dateは無計画に更新せず、テストとセットで更新する。

障害時の確認順

  1. ページ自体が開くか。開かなければAssetsまたはWorkerのデプロイを確認。
  2. ブラウザの開発者ツールで/wsがHTTP 101になっているか確認。
  3. npx wrangler tailでWorker/DO例外を確認。
  4. 最新deploymentと直前versionを確認し、変更内容を切り分ける。
  5. ローカルのnpm run checkと2クライアント試験で再現を確認。
